# Reproducible ISO builds

Goal: the same Graphite commit + the same package snapshot gives the same ISO.

## Inputs that are pinned
| Input | How |
|---|---|
| Timestamps (ISO label, version, file mtimes, squashfs, packages) | `SOURCE_DATE_EPOCH`, default = time of the last git commit (`git log -1 --format=%ct`) |
| Arch packages in the ISO | `GRAPHITE_SNAPSHOT=YYYY/MM/DD` points core/extra/multilib at the [Arch Linux Archive](https://archive.archlinux.org/repos/) for that day instead of live mirrors |
| Build container | `GRAPHITE_IMAGE`, default `docker.io/archlinux/archlinux@sha256:ef1b2d7b…` (pinned by digest, not `latest`) |
| archiso | `GRAPHITE_ARCHISO`, default `91-1`, installed from the Arch Linux Archive; the build stops if another version ends up installed |
| Container packages | with `GRAPHITE_SNAPSHOT` set, the container's own `pacman -Syu` also uses that archive day |
| Graphite packages | built by `tools/build-repo.sh` at a fixed path with `SOURCE_DATE_EPOCH` (makepkg is reproducible this way; checked by `tests/repo-sign-check.sh`) |

## Build
```sh
GRAPHITE_SNAPSHOT=2026/10/22 ./build.sh --container
```
Every build writes:
- `out/build-info.txt`: commit, SOURCE_DATE_EPOCH, snapshot, archiso version, container image, signing key (also embedded in the ISO at `/opt/graphite/build-info.txt`)
- `out/build-packages.txt`: exact package list in the ISO
- `out/<iso>.sha256`

## Checking a release
Rebuild with the values from `build-info.txt` and compare the `.sha256`. If they differ,
`diffoscope a.iso b.iso` shows where. diffoscope on two full 3 GB ISOs needs more than ~8 GB of free
RAM (it was OOM-killed on a 16 GB box); the cheaper way is to extract both ISOs with `bsdtar`, unpack
`airootfs.sfs` with `unsquashfs`, compare `sha256sum` lists of the trees, then run diffoscope only on
the files that differ.

## Double-build result (base-2, 2026-10-24)
Two builds of the same commit (c869656), same pins (`GRAPHITE_SNAPSHOT=2026/10/23`, pinned image
digest, archiso 91-1), one after the other on the same box. The ISOs are **not** byte-identical yet.
Same file list in both ISOs; every package and every other file is identical except:

| File | Why it differs | Fix (planned) |
|---|---|---|
| `etc/brlapi.key` | random key generated when brltty is installed | remove in the profile; regenerate at first boot |
| `etc/iscsi/initiatorname.iscsi` | random IQN generated by open-iscsi's install hook | remove; generate at first boot (`iscsi-iname`) |
| `etc/nvme/hostid`, `etc/nvme/hostnqn` | random UUID/NQN from nvme-cli's install hook | remove; generate at first boot |
| `var/cache/ldconfig/aux-cache` | ldconfig cache with inode/mtime data | delete before squashing |
| `opt/graphite-repo/graphite.{db,files}[.tar.zst]` | `repo-add` writes build-time data into the DB (2 bytes longer in one build); the packages themselves are identical | build the DB with a fixed `SOURCE_DATE_EPOCH`/sorted input, or normalise after `repo-add` |
| `airootfs.sfs`, `airootfs.sha512` | follow from the files above | none needed once those are fixed |

The four random-ID files are also a privacy issue: today every live boot of one ISO shares them.


## Known gaps
- Without `GRAPHITE_SNAPSHOT`, live mirrors are used and builds are only reproducible on the same day.
- Byte-identical ISOs: not yet. A double build differs only in the files listed above. Graphite packages and all other files are identical.
